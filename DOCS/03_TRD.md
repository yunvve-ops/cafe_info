# TRD 초안

[PRD](C:/CAFE/Docs/01_PRD.md)와 [FRD](C:/CAFE/Docs/02_FRD.md), `Design/1~4`의 화면 시안과 디자인 규칙을 기준으로 정리했습니다. **FRD 1.0의 기능 범위와 계산 기준을 그대로 따르며, 코드는 작성하지 않았습니다.** PRD에는 수업 범위가 확인 대기라고 적혀 있고, FRD에는 추천 범위를 반영한 확정안이라고 적혀 있어 아래 초안은 FRD 1.0을 작업 기준으로 삼되, PRD의 확인 상태는 미정으로 남깁니다.

## 사용할 기술과 선택 이유

- **Next.js + TypeScript**: 웹 화면과 서버 처리를 한 프로젝트 안에서 구성합니다. TypeScript는 날짜·금액처럼 잘못 연결되면 오류를 일으키기 쉬운 값의 형태를 미리 확인하는 데 도움이 됩니다. 화면 조회와 저장은 서버에서 처리하는 방식을 권합니다. [Next.js App Router](https://nextjs.org/docs/app)는 파일 중심으로 화면을 구성하고 서버 기능을 함께 사용할 수 있습니다.
- **Tailwind CSS**: 시안의 색과 글꼴, 화면 크기별 배치를 적용하는 데 사용합니다. 시안의 색·표현은 참고하되, FRD에서 제외한 영업 마감 확정, 안전재고 경고, CSV 내보내기 같은 버튼·기능은 추가하지 않습니다.
- **Supabase PostgreSQL**: 판매·비용·재고처럼 서로 연결되는 기록을 영구 저장합니다. 자료 관계를 유지하고, 날짜별 기록을 빠르게 합산하는 데 적합합니다. 데이터베이스는 서울 리전(`ap-northeast-2`)을 권합니다. [Supabase 리전 안내](https://supabase.com/docs/guides/platform/regions)
- **정밀 숫자 계산**: 데이터베이스에는 `NUMERIC` 형식으로 값을 저장하고, 서버 계산에서는 `decimal.js`처럼 소수 계산을 다루는 도구를 사용합니다. 일반적인 컴퓨터 소수 계산에서 생길 수 있는 오차를 줄이고, FRD처럼 원화 반올림은 최종 표시 단계에서만 합니다. [decimal.js](https://github.com/MikeMcl/decimal.js/)
- **ExcelJS**: 수업 후 범위인 `.xlsx` 양식 생성과 판매·비용 파일 읽기에 사용합니다. [ExcelJS](https://github.com/exceljs/exceljs)

Supabase Pro에는 7일 보관 일일 백업이 포함됩니다. [Vercel Pro 요금](https://vercel.com/docs/plans/pro-plan), [Vercel 요금 안내](https://vercel.com/pricing), [Supabase 요금·백업 안내](https://supabase.com/pricing). 시점에 따라 가격은 달라질 수 있습니다.

## 처리 순서

1. 사용자가 판매·비용·재고를 입력하거나 조회를 요청합니다.
2. 서버가 입력값, 기준 정보 연결 여부, 사용 권한을 확인합니다.
3. FRD의 계산 규칙에 따라 순매출·메뉴 기여액·손익·재고 잔량을 계산합니다. 누락된 원가를 0으로 간주하지 않고 확인 필요로 표시합니다.
4. 유효한 입력만 데이터베이스에 저장합니다. 판매 저장과 당시 원가 기록은 한 작업으로 처리해 일부만 저장되는 일을 막습니다.
5. 저장이 성공한 경우에만 화면의 집계와 재고를 갱신합니다. 최신 판매·비용·재고 데이터는 기간별로 서버에서 조회·합산해 오래된 값이 남지 않게 합니다.

엑셀 가져오기와 복원은 파일을 먼저 검증하고 결과 건수를 보여준 뒤 적용합니다. 한 행이라도 유효하지 않으면 전체 가져오기를 취소하는 FRD 기준을 유지합니다. 저장 묶음 처리(트랜잭션)는 전부 성공하거나 전부 취소되도록 데이터베이스가 처리하는 방식입니다. [Next.js 서버 작업 보안 지침](https://nextjs.org/docs/app/getting-started/mutating-data)

## 주요 파일이 맡는 일

아래 경로는 **향후 개발 시 제안하는 구성**이며, 현재 존재하는 코드 파일을 뜻하지 않습니다.

- `app/`: 대시보드, 판매 기록, 메뉴 수익성, 비용·재고 화면
- `src/lib/calculations/`: FRD의 메뉴 기여액, 손익, 재고, 기간 집계 계산
- `src/lib/server/`: 서버 전용 데이터 조회·저장과 권한 확인
- `src/lib/import-export/`: 엑셀 양식·가져오기와 JSON 백업·복원 처리
- `supabase/migrations/`: 데이터베이스 표와 접근 권한 변경 이력
- `tests/unit/`, `tests/integration/`, `tests/e2e/`: 계산, 저장·복원, 사용자 흐름 검증
- 기존 `Design/`: 시안 참고 자료. 실제 데이터와 FRD를 우선합니다.

## 데이터 저장·이동·복구

- 데이터베이스는 공급사·재료·메뉴·레시피·가격 이력과 판매·비용·재고 기록을 분리해 저장하고 ID로 연결합니다. 판매에는 FRD에 정해진 **날짜·메뉴·채널 집계** 구조를 사용합니다. 같은 날짜·메뉴·채널 입력은 합산하고, 수정은 집계 행을 바꾸며 삭제는 해당 행 전체를 제거합니다.
- 원자료의 빈칸은 숫자 0과 구분해 저장합니다. 과거 판매의 당시 가격·원가는 스냅샷(판매 시점 값의 보존본)으로 유지합니다. 신규 판매에는 판매일에 적용되는 레시피와 가격 이력을 씁니다.
- 실제 손익은 날짜별 비용 기록을 사용하고 월 비용 계획과 중복 합산하지 않습니다. 재료 입고액도 별도 비용으로 다시 더하지 않습니다. 이는 FRD의 비용·손익 기준을 데이터 처리에서도 지키기 위함입니다.
- 최초 샘플 적재는 같은 가상 매장 자료인 Excel·JSON 중 **한 형식만** 사용합니다. JSON을 우선 후보로 권하지만, 이 선택은 아직 승인되지 않았습니다. PRD에는 자료 경로가 `C:\CAFE\E`로 적혀 있지만 현재 제공 파일은 `C:\CAFE\Data`에 있으므로, 최초 적재 전에 참조 경로를 맞춰야 합니다.
- 수업 후 엑셀 가져오기는 판매·비용 두 시트를 검증한 뒤 한 번에 저장합니다. 같은 판매 집계의 교체·동일 파일 재가져오기·비용 행 중복 방지는 FRD의 규칙을 따릅니다.
- 전체 백업은 JSON 파일로 내려받고, 복원 전 현재 데이터의 안전 사본을 만든 뒤 전체 교체합니다. 복원 검증 실패·취소·저장 오류 시에는 기존 데이터를 유지합니다. 큰 파일은 Vercel 함수의 요청·응답 4.5MB 제한을 고려해 비공개 저장소의 제한 시간 다운로드 주소로 전달하는 방식을 권합니다. [Vercel 함수 제한](https://vercel.com/docs/functions/limitations)
- 제공 자료는 가상 샘플입니다. 실제 매장 데이터를 미리보기 배포에 넣지 않고, 운영 데이터를 GitHub 저장소에도 포함하지 않는 구성을 권합니다.

## 정보 보호

- 매출·비용은 개인식별정보가 아니더라도 민감한 영업 정보로 취급합니다. 고객 이름·결제정보는 현재 FRD 범위에 없으며 저장하지 않습니다.
- Supabase의 행 수준 보안(RLS: 데이터 행마다 읽기·쓰기 권한을 검사하는 규칙)을 적용합니다. 서비스 비밀 키는 브라우저에 보내지 않고 서버 환경 변수로만 보관합니다. [Supabase 보안 안내](https://supabase.com/docs/guides/database/secure-data)
- FRD에는 로그인 화면이 정해져 있지 않습니다. 다만 인터넷에 배포한 운영 자료를 보호하려면 접근 통제가 필요합니다. **권장안은 운영자 1명 로그인, 공개 회원가입 없음**입니다. 이는 FRD에 없는 화면·접근 조건이므로 승인 전에는 확정 기능으로 취급하지 않습니다.
- GitHub 저장소는 비공개로 두고, 미리보기 배포는 운영 데이터베이스와 분리합니다. Vercel 환경 변수는 코드 저장소에 올리지 않습니다. [Vercel 환경 변수 안내](https://vercel.com/docs/environment-variables)

## 오류 대응

- 입력값은 서버에서 다시 검증합니다. 누락·잘못된 ID·할인 초과·단위 불일치·미래 판매일은 저장하지 않고 수정할 항목을 알립니다.
- 저장 실패나 연결 끊김에는 성공 메시지를 표시하지 않고 입력을 보존합니다. 재시도 과정에서 같은 요청이 중복 저장되지 않도록 요청 단위를 확인합니다.
- 레시피·재료 가격이 없으면 원가를 0원으로 만들지 않고 “확인 필요”로 표시합니다. 자료가 없는 기간도 0원 대신 “기록 없음”으로 구분합니다.
- 엑셀 손상·열 누락·오류 행·중복 등은 시트와 행을 가리켜 안내하고, 전체 미반영 원칙을 지킵니다. Vercel 제한을 넘은 파일은 잘라 처리하지 않고 재시도 가능한 오류로 안내합니다.
- 백업 형식·연결된 기준 정보·자료 건수 검증에 실패하면 복원하지 않습니다. 데이터베이스 오류는 상세 내부 정보 대신 사용자 안내와 오류 식별값을 보여주고, 로그에는 판매 금액·백업 내용 같은 원문을 남기지 않습니다.

## 배포 방법

- 코드는 GitHub 비공개 저장소에 보관하고, Vercel을 저장소에 연결합니다. 기본 브랜치의 변경은 운영 배포, 다른 브랜치와 PR은 미리보기 배포로 사용합니다. [Vercel GitHub 연동](https://vercel.com/docs/git/vercel-for-github)
- 미리보기에는 시험용 Supabase 프로젝트와 가상 자료를 연결합니다. 운영 데이터베이스로 미리보기 기능을 시험하지 않습니다.
- Supabase 데이터 구조와 권한 변경은 버전 기록이 남는 마이그레이션 파일로 관리합니다. 운영 배포 전에 미리보기에서 계산·저장·복원 흐름을 확인합니다.
- 수업 4시간에는 FRD의 수업 중 범위인 FR-01~FR-07에 집중합니다. FR-08 엑셀, FR-09 예상 손익, FR-10 발주량 참고, FR-11 백업·복원과 주·분기·반기·연간 조회는 수업 후 확장으로 유지합니다.

## 확인 방법

- **계산 단위 확인:** 1개당 재료 원가 460원인 메뉴를 2개, 단가 4,000원, 할인·수수료 0원으로 입력하면 순매출 8,000원, 직접 원가 920원, 기여액 7,080원, 기여율 88.5%가 되는지 확인합니다.
- **손익 확인:** 순매출 20,000원 − 원가 6,000원 − 수수료 1,000원 − 날짜별 비용 8,000원 = 5,000원인지 확인합니다. 월 비용 계획이 실제 손익에 중복 포함되지 않는지도 확인합니다.
- **재고 확인:** 장부 1,000ml + 입고 500ml − 폐기 100ml − 판매 사용 400ml = 1,000ml인지 확인합니다. 실사 920ml 입력 후 잔량이 920ml로 조정되는지 확인합니다.
- **저장·오류 확인:** 저장 후 다른 화면에 다녀와도 기록이 유지되는지, 잘못된 값은 저장되지 않는지, 삭제 후 모든 연결 집계가 바뀌는지 확인합니다.
- **파일·복원 확인:** 유효한 엑셀은 전체 반영되고 오류 행이 있는 파일은 전혀 반영되지 않는지, 같은 파일의 재가져오기가 중복을 만들지 않는지 확인합니다. 손상 백업·복원 취소 시 기존 데이터가 유지되는지도 확인합니다.
- **기본 속도 확인:** 제공 샘플의 판매 6,112건과 비용 3,560건을 기준으로 기간별 화면이 지나치게 느리지 않은지 미리보기 배포에서 측정합니다. PRD·FRD에는 응답 시간 목표가 없어 임의의 통과 기준은 만들지 않았습니다.

### 문서 저장 전 확인이 필요한 제안

- 로그인 화면과 운영자 접근 통제는 FRD에 없으므로 제품 기능으로 넣을지 승인 필요
- 최초 샘플 적재 형식은 Excel·JSON 중 하나만 사용해야 하며, JSON 우선은 미승인 제안
- 단위 수량의 허용 소수 자릿수와 복원 전 안전 사본의 보관 기간은 PRD·FRD에서 정하지 않음
- 실제 운영용 요금은 사용량과 계정 조건에 따라 달라질 수 있음
